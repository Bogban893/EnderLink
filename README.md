# EnderLinc — P2P-система для запуска и управления Minecraft-серверами
// поменять

**Концепция:** приложение, позволяющее

[//]: # (запускать Minecraft-сервер на собственном компьютере, подключать друзей без проброса портов, )

управлять сервером и передавать роль хоста другому участнику (передовать мир).

Главная особенность — **сервер не привязан к конкретному компьютеру**. Любой участник с необходимыми правами может стать новым хостом, получив сохранение мира от предыдущего.

При этом приложение работает независимо от Minecraft (работает с файлами) и предоставляет два интерфейса: CLI и GUI.

# 1. Основные возможности

## 1.1. Управление Minecraft-сервером

Пользователь может запускать Minecraft-сервер из существующего одиночного мира.

**Возможности:**
- Выбор мира из локальных сохранений Minecraft.
- (позже) Запуск Minecraft Dedicated Server без графического интерфейса.
- Остановка и перезапуск сервера.
- Просмотр состояния сервера.
- Отображение подключённых игроков (к утилите, а не в самом майне).
- Отправка серверных команд.
- Просмотр логов в реальном времени.
- (позже) Запуск Minecraft-клиента для подключения к своему серверу.

Пример CLI:

```bash
EnderLinc host start "My Survival"
EnderLinc host stop
EnderLinc host restart
EnderLinc host status
EnderLinc host logs
EnderLinc host console
```

**Особенность:** Minecraft-сервер запускается как отдельный процесс, поэтому закрытие игрового клиента или GUI не останавливает сервер.

Для первого прототипа разумно поддерживать Vanilla Minecraft Java Edition. Поддержку Paper, Fabric и Forge можно добавить позже. (мб будет работать по дефолту)

## 1.2. (позже) P2P-подключение друзей

Каждый участник устанавливает `EnderLinc`, который автоматически обнаруживает доступных друзей и позволяет подключаться к их игровым серверам.

**Возможности:**
- Регистрация узлов у координатора.
- Обнаружение друзей.
- Проверка доступности других узлов.
- Попытка установить прямое P2P-соединение.
- Автоматический переход на relay, если прямое соединение невозможно.
- Шифрование соединений.
- Автоматическое восстановление соединения после кратковременного разрыва.

Пример:

```bash
EnderLinc peers

NAME       STATUS     HOSTING
alex       online     Survival
max        online     -
steve      offline    -
```

Подключение:

```bash
EnderLinc connect alex 123
```

После этого агент создаёт локальный TCP-прокси, например:

```text
127.0.0.1:25565
```

Игрок открывает Minecraft и подключается к этому адресу.

### Как передаётся игровой трафик

```text
Minecraft Client
       |
       | TCP
       ▼
Local TCP Proxy
       |
       ▼
EnderLinc Agent
       |
       | P2P Tunnel (QUIC)
       |
       ▼
EnderLinc Agent (Host)
       |
       | TCP
       ▼
Minecraft Server
```

Minecraft ничего не знает о нашей P2P-сети.

Поэтому система не зависит от конкретного лаунчера и не требует модификации игрового клиента.

Важно: QUIC сам по себе не решает NAT traversal. Для установления прямого соединения потребуется отдельный механизм обнаружения адресов и согласования подключения.

## 1.3. Ручная передача хоста

Допустим, сервер запущен у игрока A, но он хочет выключить компьютер.

Он выполняет:

```bash
EnderLinc host transfer max
```

Далее система:

1. Проверяет готовность компьютера B принять сервер.
2. Уведомляет участников о предстоящем переключении.
3. Останавливает Minecraft-сервер на A с сохранением мира.
4. Передаёт сохранение мира и необходимые конфигурации на B.
5. Проверяет целостность переданных данных.
6. Запускает Minecraft-сервер на B.
7. Обновляет информацию об активном хосте.
8. Переключает туннели остальных участников на B.

**Результат:** игроки продолжают играть в том же мире, но теперь сервер работает на другом компьютере.

Обычные Minecraft-клиенты при переключении должны будут переподключиться. Локальный адрес останется прежним, но автоматический повторный вход без клиентского мода не гарантируется.

### Технические особенности миграции

Здесь предстоит решить несколько задач:

- Передача больших сохранений.
- Возобновление прерванной передачи.
- Проверка целостности файлов.
- Согласованность состояния мира.
- Откат при неудачной миграции.
- Защита от одновременного запуска двух активных хостов.

Можно реализовать миграцию как конечный автомат:

```text
IDLE
  |
  ▼
PREPARING
  |
  ▼
STOPPING
  |
  ▼
TRANSFERRING
  |
  ▼
VERIFYING
  |
  ▼
STARTING
  |
  ▼
SWITCHING
  |
  ▼
COMPLETED
```

При ошибке система переходит в состояние восстановления, в котором решает, можно ли безопасно вернуть управление старому хосту.

Для первой версии можно передавать мир целиком после остановки сервера. Предварительная синхронизация — возможная оптимизация на будущее.

Так же стоит изучить процесс сохранения мира во время игры и передавать его пользователю.

## 1.4. (сильно позже) Удалённое управление

Пользователь может управлять своим Minecraft-сервером с другого компьютера через `EnderLinc`.

Например:

```bash
EnderLinc remote alex status
EnderLinc remote alex players
EnderLinc remote alex logs
```

Для этого используется отдельный управляющий канал.

**Возможности:**
- Удалённый просмотр состояния.
- Просмотр логов.
- Отправка разрешённых команд.
- Перезапуск сервера.
- Инициирование передачи хоста.

Для безопасности потребуется система прав доступа.

Например:

| Роль | Права |
|---|---|
| Owner | Полное управление |
| Admin | Управление сервером |
| Player | Только подключение |
| Guest | Ограниченный доступ |

При этом права `EnderLinc` и права оператора внутри Minecraft — разные вещи.

## 1.5. Мониторинг сети

Агент собирает техническую информацию о соединениях.

Например:

```bash
EnderLinc net status
```

```text
Peer: alex
Connection: Direct P2P
RTT: 24 ms
Transport: QUIC
Relay: No
```

**Возможности:**
- Измерение RTT.
- Определение типа соединения: P2P или relay.
- Измерение скорости передачи.
- Статистика переподключений.
- Диагностика сетевых ошибок.
- Логирование событий миграции.

В дальнейшем можно добавить анализ сетевых лагов и сравнение их с серверными задержками Minecraft.

Я бы выбрал **модульную архитектуру с постоянно работающим агентом**.

Координатор нужен для обнаружения узлов и согласования подключений. При невозможности прямого соединения игровой трафик идёт через relay-инфраструктуру.

## 2.2. EnderLinc-agent

**Главный компонент системы.**

Работает в фоновом режиме и не зависит от открытого GUI или терминала.

Его внутренние модули:

| Модуль | Назначение |
|---|---|
| PeerManager | Обнаружение и учёт участников |
| ConnectionManager | Управление P2P-соединениями |
| TunnelManager | Передача игрового TCP-трафика |
| MinecraftManager | Запуск и остановка сервера |
| WorldManager | Работа с сохранениями |
| MigrationManager | Передача роли хоста |
| RemoteControl | Удалённое управление |
| MetricsCollector | Сбор сетевой статистики |

Агент также предоставляет локальный API для CLI и GUI.

На Linux его можно запускать через `systemd --user`, на Windows — как фоновое приложение или службу.

## 2.3. EnderLinc CLI

Консольная утилита, которая отправляет команды агенту.

Пример:

```bash
EnderLinc host start survival
EnderLinc peers
EnderLinc connect alex
EnderLinc host transfer max
EnderLinc status
```

Для реализации можно использовать Kotlin и `picocli`.

CLI не содержит собственной сетевой логики.

## 2.4. EnderLinc GUI

Графическое приложение на Kotlin + Compose Desktop.

Основные экраны:

- Главная страница с состоянием сервера.
- Список друзей.
- Управление Minecraft-сервером.
- Передача хоста.
- Мониторинг сети.
- Настройки.

GUI взаимодействует с тем же агентом, что и CLI.

Таким образом, можно одновременно пользоваться терминалом и графическим интерфейсом.

## 2.5. Coordinator

Небольшой сервер, доступный через интернет.

**Его задачи:**
- Регистрация подключённых агентов.
- Аутентификация пользователей и узлов.
- Обнаружение друзей.
- Обмен информацией, необходимой для NAT traversal.
- Помощь в согласовании P2P-соединений.

Координатор не должен хранить Minecraft-миры или управлять игровыми серверами.

При успешном P2P-соединении игровой трафик проходит напрямую между участниками.

Relay можно реализовать отдельным компонентом или разместить рядом с координатором.

# 6. Что будет технически интересного на защите

Я вижу три основные исследовательские задачи.

### I. Установление P2P-соединений

Исследовать, как устройства за NAT могут устанавливать соединения без ручного проброса портов.

Разработать протокол передачи роли хоста.

### III. Минимизация времени простоя

Измерить время миграции при разных размерах миров и характеристиках сети.

В качестве оптимизации можно исследовать предварительную передачу неизменившихся данных мира.

# 7. Как будет выглядеть использование

Представим трёх друзей: A, B и C.

**Шаг 1.** Все запускают `EnderLinc`. Агенты регистрируются у координатора.

**Шаг 2.** A запускает мир:

```bash
EnderLinc host start survival
```

**Шаг 3.** B и C видят доступный сервер:

```bash
EnderLinc peers
```

**Шаг 4.** Они подключаются:

```bash
EnderLinc connect A
```

**Шаг 5.** A хочет выключить компьютер и передаёт сервер B:

```bash
EnderLinc host transfer B
```

**Шаг 6.** Мир сохраняется и передаётся B. Новый сервер запускается, а агенты перенаправляют подключения.

**Шаг 7.** Игроки переподключаются к Minecraft и продолжают играть.

При этом A может выключить компьютер.

# 8. Что я бы ещё обсудил перед началом разработки

Есть несколько архитектурных решений, которые пока не зафиксированы.

**1. Нужно ли делать полноценную виртуальную локальную сеть?**

Сейчас мы планируем TCP-туннель только для Minecraft.

Это проще и позволяет обойтись без виртуальных сетевых адаптеров.

Но можно сделать универсальный VPN-подобный инструмент, который будет работать и с другими играми. Это значительно увеличит объём разработки.

**2. Как передавать мир?**

Самый простой вариант — после остановки сервера передавать все файлы.

Более интересный — использовать предварительную синхронизацию и передавать только изменившиеся данные.

Второй вариант позволит уменьшить простой, но усложнит реализацию.

**3. Как управлять доступом?**

Можно сделать постоянные группы друзей с приглашениями.

Либо ограничиться списком доверенных узлов, которые могут подключаться друг к другу.

**4. Как обеспечить безопасную миграцию?**

Нужно решить, кто имеет право объявить себя новым хостом и как предотвратить запуск двух независимых копий мира.

Для ручной миграции можно использовать протокол передачи полномочий с подтверждением нового хоста и возможностью отката.
