# AGENTS.md

Инструкции для работы с EnderLink — многомодульным Kotlin/JVM-приложением для передачи миров Minecraft Java, хранения их версий и управления локальным сервером.

## 1. Принципы работы

- Перед изменением прочитай соседний код, конфигурацию модуля и относящуюся к задаче документацию. Проверяй API по реализации, не придумывай существующие возможности.
- Делай минимальные изменения, необходимые для задачи. Не проводи массовый рефакторинг, переименование или переформатирование без запроса.
- Сохранность миров, целостность передачи и предсказуемое завершение сервера важнее косметического единообразия.
- Повторно используй общую реализацию. Не создавай отдельные протоколы, хранилища и правила обработки конфликтов для GUI и CLI.
- Различай реализованное поведение и планы. Основной README содержит оба вида сведений; сверяй его с кодом и руководствами модулей.
- Разрешай обычные технические вопросы по существующим паттернам. Существенные допущения указывай явно; уточняй требования, если выбор меняет пользовательское поведение или сохранность данных.
- Явные указания пользователя имеют приоритет над правилами этого файла. Не расширяй задачу до всей описанной здесь архитектурной миграции.

## 2. Структура и текущее состояние

```text
core/               транспорт TCP/iroh, профили, передача данных, версии миров
agent/              процесс Vanilla-сервера, режим host-service, игровой туннель
cli/                консольные команды профиля, чата, файлов и миров
desktop/            Swing GUI, установка мира в Minecraft saves
connectivity-test/  отдельный эксперимент WebRTC
iroh-test/          диагностический чат поверх iroh из core
docs/               форматы миров и сценарии ручной проверки
scripts/            воспроизводимые вспомогательные сценарии
```

Исходники лежат в `src/main/kotlin`, тесты — в `src/test/kotlin`; в `agent` есть Java-исходник тестового процесса. Корневой пакет — `org.enderlink`; сохраняй принятую структуру пакетов соответствующего модуля.

Текущие зависимости:

```text
desktop → agent → core
   └───────────→ core
cli ───────────→ core
iroh-test ─────→ core
```

`connectivity-test` — самостоятельный стенд. Корневой `src/main/kotlin/org/enderlink/Main.kt` содержит учебный код и не является точкой входа EnderLink.

Сейчас `agent` одновременно предоставляет используемые GUI серверные классы и собственные команды `host`, `host-service`, `tunnel-host`, `tunnel-join`. Он не является автоматически установленным демоном. `host-service` работает на переднем плане без чтения stdin и подходит для менеджера служб. CLI пока не зависит от `agent`; общего локального API между процессами нет.

## 3. Направление развития архитектуры

Согласованное направление для переработки интерфейсов:

```text
desktop → agent → core
cli ────→ agent
```

- **core** предоставляет транспорт, протоколы, проверку данных, файловые операции и хранилище версий. Он не зависит от GUI, CLI или управления Minecraft-процессом.
- **agent** координирует прикладные операции и их состояние: запуск и остановку серверной сессии, публикацию и передачу мира, жизненный цикл туннеля. Общие последовательности действий и правила восстановления должны жить здесь.
- **cli** отвечает за команды, интерактивные вопросы, пользовательский вывод, отображение прогресса и коды завершения.
- **desktop** отвечает за окна, пользовательский ввод и отображение состояния. Длительные операции выполняются вне потока Swing.

При переработке CLI добавляй зависимость от `agent` для общих прикладных операций. Переноси общую координацию из интерфейсов постепенно, в рамках задачи. Прямое использование моделей и низкоуровневых API `core` допустимо; избегай дублирования прикладных сценариев. Не вводи пустые обёртки только ради графа зависимостей.

Зависимость от модуля и обращение к отдельному процессу — разные механизмы. Полноценный постоянный агент с локальным API — отдельный этап: он должен владеть серверным процессом, соединениями и состоянием операций, а интерфейсы — управлять ими. Вызов классов внутри процесса CLI сам по себе не обеспечивает работу после завершения команды или доступ к той же сессии из следующего запуска CLI. Не описывай демон, IPC и автозапуск как готовые возможности до их реализации.

- Циклические зависимости запрещены. `agent` не должен зависеть от `cli` или `desktop`.
- Создавай новый модуль или интерфейс при наличии полезной границы ответственности. Слои `domain/data/presentation`, отдельные use case, DI-фреймворк и интерфейс для каждого класса не обязательны.
- Используй ручную передачу зависимостей через конструкторы и параметры. Избегай скрытого глобального изменяемого состояния.

## 4. Сохранность миров и данных игроков

- Публикуй согласованное сохранение: одиночный мир должен быть закрыт, сервер остановлен. Проверка файлов во время чтения не заменяет согласованный снимок.
- Разделяй исходный мир, хранилище EnderLink, копию серверной сессии и установленный мир в Minecraft `saves`. Не допускай опасного пересечения каталогов.
- Сохраняй модель `WorldRepository`: `world` — рабочая копия; `.enderlink` — манифесты, объекты, активная версия, staging и предыдущая копия.
- Неполная или непроверенная версия не становится активной. Проверяй размеры и SHA-256 объектов и собранного дерева до переключения.
- Сохраняй атомарность переключения и восстановление после сбоя. Учитывай требования переименования на одном томе и дополнительное место под объекты, сборку и предыдущую копию.
- Не затирай неопубликованные локальные изменения. При расхождении версий сохраняй обе ветки; выбор другой ветки должен быть явным. Автоматическое объединение миров не реализовано.
- Повторная передача должна использовать уже проверенные данные. Не удаляй историю или состояние докачки как побочный эффект несвязанной задачи.
- При установке в `saves` сохраняй проверку `session.lock` и защиту локально изменённого мира.
- Сохраняй данные игроков в поддерживаемых расположениях `playerdata` и `players/data`. Перенос владельца из старого `level.dat` требует явного UUID и не должен перезаписывать существующий файл игрока или менять исходный мир.
- Сохраняй требование `online-mode=true` при управляемом запуске сервера: идентичность игрока важна при смене хоста.

## 5. Сеть, форматы и безопасность

- Общая абстракция транспорта — `Connection`: целые сообщения, один читатель, возможность параллельной отправки. Сохраняй её контракт при изменениях TCP и iroh.
- Файлы, каталоги и версии миров имеют свои протоколы поверх общего соединения. Не смешивай их форматы и режимы согласования.
- Для миров сейчас используются новые манифесты формата 2, блоки по 256 КиБ и сетевой протокол `ELW4`; поддерживается чтение хранилищ формата 1. Уточняй детали в `docs/world-versions.md` и коде.
- Изменение протокола, схемы хеширования или дискового формата требует явного решения о совместимости, версии и миграции. Обновляй документацию и проверки обеих сторон; несовместимая сторона должна получать понятный отказ.
- Проверяй входящие пути, размеры, количества элементов и хеши. Не допускай выхода за каталог назначения, обхода через ссылки и неограниченного выделения памяти по данным собеседника. Большие файлы обрабатывай потоково.
- TCP не предоставляет шифрования и аутентификации и предназначен для доверенной сети. iroh использует проверку ID друзей и защищённое соединение; не обходи эти проверки ради подключения.
- Публичный поиск и relay iroh — внешние зависимости. Учитывай таймауты и недоступность; успешное соединение не доказывает прямой маршрут.
- Профиль по умолчанию — `~/.enderlink/iroh-test`, общий для использующих его приложений. Сохраняй блокировку профиля, постоянный ID и права доступа к `secret.key`. Не заменяй повреждённый ключ автоматически.
- Не помещай секретные ключи, токены и содержимое приватного профиля в репозиторий, сообщения и логи. Локальный файл ключа с ограниченными правами — часть текущей реализации профиля.

## 6. Процессы, асинхронность и ошибки

- Сервер запускается отдельным процессом из проверенной копии мира. Пользователь принимает EULA самостоятельно; версия серверной Java и `server.jar` должна соответствовать Minecraft.
- Штатная остановка включает сохранение, команду `stop`, ожидание завершения и публикацию только после успешного выхода. При ошибке или таймауте сохраняй каталог сессии и сообщай путь к миру и журналу.
- Сейчас следующий запуск требует новой серверной сессии без существующего `world`; GUI создаёт её автоматически. Не обещай безопасный автоматический рестарт с прежним каталогом без отдельной реализации.
- У сокета, слушателя, профиля, потока и процесса должен быть понятный владелец. Закрывай ресурсы через `use`/`finally`; отмена должна разблокировать ожидание и освобождать ресурсы.
- Существующий блокирующий API допустим. Не переводи весь проект на `suspend`/`Flow` ради единообразия. Блокирующий I/O запрещён в Swing EDT; обновляй UI через механизмы Swing.
- При использовании корутин соблюдай структурированную конкурентность, не используй `GlobalScope`, не проглатывай `CancellationException`. Блокирующий I/O внутри корутин выполняй на подходящем диспетчере; делай зависимости подменяемыми там, где это нужно для тестов.
- Сохраняй контекст ошибок. Текущие API используют `IOException`, включая `WorldConflictException`, и `require`/`check` для предусловий; не вводи второй общий механизм ошибок без необходимости.
- Подавление ошибки допустимо для ожидаемой ситуации или освобождения ресурсов, если оно не скрывает провал основной операции. Отмена и прерывание не должны выглядеть как успешное завершение.
- Пользовательский вывод CLI и справка через stdout, ошибки через stderr допустимы. Служебные компоненты по возможности сообщают события через переданный обработчик или отдельный механизм логирования; не смешивай диагностику с пользовательским результатом.

## 7. Организация Kotlin-кода и зависимостей

- Один файл — одна связная ответственность. Основной тип обычно задаёт имя файла; небольшие связанные модели, исключения и приватные функции можно держать рядом.
- Большой файл — повод оценить разделение по ответственности, а не требование механически разнести каждый тип. Не объединяй независимые UI, сетевые и файловые операции в одном компоненте.
- Используй `val`, понятные имена, узкую видимость и именованные аргументы там, где это снимает неоднозначность. Избегай `!!`, скрытых побочных эффектов и файлов со случайным набором утилит.
- Публичный API может включать конкретные классы. Документируй неочевидные контракты: блокирующее поведение, владение ресурсами, потокобезопасность, ошибки и влияние на файлы.
- Сохраняй стиль соседнего кода. Комментарии объясняют причины и ограничения; отложенные задачи должны содержать контекст.
- Сейчас зависимости и версии объявлены в `build.gradle.kts`; version catalog, convention plugins, explicit API mode, ktlint и detekt не настроены. Не требуй отсутствующих инструментов и не подключай их попутно.
- Новые библиотеки и модули добавляй при доказанной необходимости. Не меняй версии Java, Kotlin, Gradle и зависимостей вне задачи, которая этого требует.

## 8. Проверки и запуск

Используй JDK 21 и Gradle Wrapper проекта. Тесты используют `kotlin.test` и JUnit Platform. Выбирай проверки по затронутому поведению.

```bash
# Сборка и тесты всего проекта
./gradlew build

# Пример проверки отдельного модуля
./gradlew :core:test

# Сборка основных приложений
./gradlew :cli:installDist :agent:installDist :desktop:installDist

# Запуск GUI
./gradlew :desktop:run

# Справка собранных консольных приложений
./cli/build/install/cli/bin/cli --help
./agent/build/install/agent/bin/agent --help
```

В Windows используй `gradlew.bat` и соответствующие `.bat`-скрипты дистрибутивов. Для интерактивной консоли удобнее собранный скрипт; для GUI нужна графическая сессия. Нативные транспорты имеют ограничения платформ; полный набор тестов WebRTC на Linux требует системных библиотек, перечисленных в `connectivity-test/README.md`.

- Проверяй исправления ошибок воспроизводящими тестами; изменения протоколов и хранилища — тестами контрактов и отказов. Для простой правки документации достаточно сверить команды, ссылки и форматирование.
- Тестируй наблюдаемое поведение, а не приватную реализацию. Интеграционный тест может охватывать несколько классов; не требуется соответствие «один класс — один тестовый класс».
- Обычные тесты не должны зависеть от публичного интернета, реальных аккаунтов и установленного Minecraft. Локальные TCP/iroh/WebRTC-тесты допустимы: ограничивай ожидания, используй свободные порты и гарантированное освобождение ресурсов.
- Для файлов используй временные каталоги, для процессов — тестовые процессы. Проверяй обрывы, повреждение данных, конфликт версий, восстановление и корректную остановку там, где это затрагивает задача.
- Настоящий Minecraft, NAT между разными сетями, relay и сохранность инвентаря при входе требуют отдельной ручной проверки по `docs/manual-acceptance.md`. Не выдавай локальный тест за её подтверждение.
- Не отключай проверки ради успешной сборки. Указывай выполненные проверки и оставшиеся ограничения; тесты без новых изменений и причин повторять не нужно.

## 9. Документация и завершение задачи

Основные источники:

- `desktop/README.md` — GUI и установка мира в Minecraft.
- `cli/README.md` — реальные команды, передача и докачка.
- `agent/README.md` — серверные сессии, host-service и игровой туннель.
- `docs/world-versions.md` — форматы, хранилище и протокол передачи мира.
- `docs/player-data-and-ux.md` — данные игроков и пользовательские сценарии.
- `docs/manual-acceptance.md` — проверка настоящего Minecraft и двух компьютеров.

При изменении пользовательского поведения обновляй соответствующее руководство и справку команды. Не представляй примеры будущих команд из README как реализованные.

Перед завершением проверь:

- Изменения соответствуют задаче, границы модулей сохранены, прикладная логика не дублируется в интерфейсах.
- Сохранность мира, совместимость форматов, завершение процессов и освобождение ресурсов учтены в затронутом сценарии.
- Выполнены подходящие проверки; их результаты и непроверенные условия описаны честно.
- Нет секретов, сгенерированных файлов и случайных изменений. Не затирай пользовательские правки и не переписывай историю без запроса. Создавай коммиты только по запросу.
- В итоговом ответе кратко указаны результат, проверки и существенные ограничения.
