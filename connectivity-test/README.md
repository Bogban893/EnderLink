# Проверка прямого соединения через WebRTC

Временный самостоятельный Kotlin/JVM-модуль на
[webrtc-java 0.20.0](https://github.com/devopvoid/webrtc-java).
Java-код писать не требуется. Модуль не использует `core` или `cli`.

Две программы обмениваются файлами приглашения и ответа через любой мессенджер,
затем пробуют открыть защищённый канал данных напрямую. TURN/relay не
настраивается; приглашения с relay-кандидатами отклоняются. STUN помогает узнать
внешний адрес, но не пересылает чат. Работа через любой NAT не гарантируется.

## Сборка

Нужна Java 21. На каждом компьютере из корня проекта:

```bash
./gradlew :connectivity-test:installDist
```

Сборка выбирает нативную библиотеку под ОС и архитектуру компьютера, на котором
запущен Gradle. Поддерживаются Linux, Windows и macOS (x64/arm64), также Linux
arm32. Если передаёте готовую сборку, собирайте её под ОС и архитектуру получателя.

На Linux нативному WebRTC нужны системные библиотеки даже без видео. Для
Ubuntu/Debian, если загрузка библиотеки завершается ошибкой:

```bash
sudo apt-get install libx11-6 libxext6 libxfixes3 libxdamage1 libxtst6 libxrandr2 libxcomposite1 libglib2.0-0 libgbm1 libdrm2
```

Источник: [требования библиотеки](https://jrtc.dev/guide/get-started).

## Проверка на двух компьютерах

Для проверки NAT используйте **разные сети**, например домашний интернет одного
друга и домашний интернет другого. Отключите VPN, если хотите проверить именно
прямой путь через своих провайдеров. В одной Wi-Fi-сети тоже можно проверить
работу программы, но это не проверяет соединение через интернет.

**Первый компьютер:**

```bash
./connectivity-test/build/install/connectivity-test/bin/connectivity-test offer offer.txt
```

Дождитесь сообщения, что `offer.txt` готов. Отправьте его другу как файл через
мессенджер. **Не закрывайте программу**: она ждёт путь к ответу.

**Второй компьютер:** сохраните приглашение и запустите:

```bash
./connectivity-test/build/install/connectivity-test/bin/connectivity-test answer offer.txt answer.txt
```

Дождитесь готовности `answer.txt` и сразу отправьте его обратно. Оставьте второй
процесс запущенным. На первом компьютере сохраните ответ и введите путь к нему
в ожидающую программу (без кавычек, даже если путь содержит пробелы).
Если путь неверный, файл недоступен или имеет неправильный формат, программа
попросит ввести путь ещё раз. То же происходит с неверным путём приглашения
в команде `answer`. `/quit` или конец ввода отменяют ожидание.

После создания ответа второй процесс ждёт открытия канала до 5 минут.
Если WebRTC раньше сообщает `FAILED`, ожидание заканчивается сразу: увеличение
таймаута приложения не заставляет сетевой стек продолжать неудачную попытку.
Если не успели обменяться файлами или соединение не установилось, перезапустите обе
стороны с новыми именами файлов. Существующие файлы не перезаписываются.
Приглашение привязано к живому процессу и текущей сети, это не постоянный ID группы.

После сообщения `Канал открыт`:

- Введите текст: он появится у друга. Проверьте обе стороны.
- Введите `/probe`: отправятся 16383 случайных байта и байт типа сообщения.
  Получатель вычислит SHA-256 и пришлёт подтверждение; отправитель сравнит хеш.
- `/quit` или конец ввода завершает сессию.

В Windows используйте `gradlew.bat` и
`connectivity-test\build\install\connectivity-test\bin\connectivity-test.bat`.
Для интерактивного ввода готовый скрипт удобнее, чем `gradlew :connectivity-test:run`.

## Диагностика

По умолчанию используется `stun:stun.l.google.com:19302`. Можно указать другой
доступный STUN (адрес и порт задаются владельцем сервиса):

```bash
./connectivity-test/build/install/connectivity-test/bin/connectivity-test offer offer.txt --stun stun:stun.example.org:3478
```

Такая же опция есть у `answer`. Для локальной проверки без внешних запросов
добавьте `--no-stun` **на обеих сторонах**.

Логи показывают состояния ICE и соединения, типы найденных кандидатов и
выбранный адрес. `host` — адрес интерфейса, `srflx` — адрес, полученный через STUN,
`prflx` — адрес, обнаруженный при проверке связи. Тип `host` сам по себе не
означает локальную сеть: это может быть и публичный IPv6.

Открытый канал и успешная `/probe` подтверждают передачу между этими двумя
компьютерами в текущих сетях. VPN или внешние туннели могут изменить маршрут;
отсутствие TURN не доказывает отсутствие VPN. Неудача не определяет однозначно
тип NAT: проверьте ошибки STUN, межсетевой экран, актуальность файлов и оба
работающих процесса. Межсетевой экран ОС может запросить разрешение для Java.

Файлы содержат сетевые адреса, временные параметры сессии и отпечаток сертификата.
Передавайте их своему собеседнику через доверенный канал. Регистрации, групп,
постоянных профилей и передачи пользовательских файлов в этом тесте пока нет.

## Автоматическая проверка

```bash
./gradlew :connectivity-test:test
```

Тест поднимает две нативные WebRTC-стороны без STUN/TURN, проводит полный обмен
приглашением/ответом и проверяет бинарные данные и UTF-8 в обе стороны.
Это локальная проверка реализации, а не тест NAT вашего провайдера.
