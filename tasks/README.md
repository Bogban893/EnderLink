# Задачи и прогресс EnderLink

Подробный список пользовательских улучшений с критериями и исходной нумерацией —
[B01–B17](backlog.md). Ближайший фокус — передача миров, данные игроков и удобство
интерфейсов. В B02 выбран общий процесс агента: CLI и GUI отправляют команды и
получают уведомления об изменениях. Запуск отдельного Minecraft-сервера без активного
участия хоста, игровой туннель и миграция сервера отложены. Интернет-передача миров
через свой координатор остаётся в плане. CI уже работает по сообщению пользователя, отдельного ремонта нет.

## Как отмечать прогресс

- `[x]` — конкретный критерий выполнен. `[ ]` — работа или подтверждение ещё нужны.
- У критерия реализации отметка означает наличие кода и соответствующих тестов,
  если они указаны. Это не подтверждает ручную приёмку на физических компьютерах.
- При выполнении критерия добавляйте основание: тест, коммит, путь к отчёту,
  дату и окружение ручной проверки. Затем обновляйте статус родительской задачи.
- Этап закрывается после всех обязательных критериев, включая приёмку. Не считайте
  общий процент по количеству галочек: трудоёмкость критериев различается.
- Актуальный прогресс ведётся здесь и в подзадачах. `concept.md` хранит исходные
  идеи; старый корневой план развития — исторический материал, если он присутствует.

Начальное состояние сверено по исходникам и тестам 24 ноября 2026 года.
Тесты при составлении этой декомпозиции не запускались заново. Неизвестные результаты
реальных испытаний оставлены открытыми; команда может отметить их после добавления отчётов.

## 2. Собственный координатор и интернет-связь

Рабочее направление: сервер обнаружения с публичным IP. Текущая интернет-передача
уже использует iroh и внешние сервисы поиска/relay; переход на свою инфраструктуру
не означает повторной реализации файлового транспорта.

- [x] Есть защищённый транспорт iroh, постоянные ID, друзья и локальные интеграционные тесты.
- [ ] Зафиксировать роли инфраструктуры: наш сервер обнаруживает участников; отдельно определить путь игровых данных и миров — напрямую, через relay или всегда через сервер.
- [ ] Описать API регистрации узла, подтверждение владения ID, heartbeat/TTL, поиск разрешённого друга и ограничения доступа к сведениям об участниках.
- [ ] Реализовать координатор и настройку его адреса в клиенте; обработать недоступность сервера и устаревшие записи.
- [ ] Интегрировать найденные сведения с текущим транспортом; проверить возможности используемых Kotlin-привязок iroh до выбора конкретного API.
- [ ] Определить fallback: существующий relay или свой. Собственный relay разворачивать при необходимости; это отдельная роль, даже если он работает на том же сервере.
- [ ] Развернуть сервис с защищённым доступом на машине с публичным IP; описать конфигурацию и перезапуск.
- [ ] Проверить две домашние сети, мобильную точку доступа, смену адреса, повторное подключение и перезапуск координатора.

Публичный IP координатора делает доступным координатор. Он не делает автоматически
доступными входящие порты клиентов за NAT. Если прямой путь невозможен, нужен relay
либо выбранная передача всего трафика через сервер. Во втором случае надо учитывать
его пропускную способность и зависимость всех сессий от сервера.

Справка: [сервисы обнаружения и relay iroh](https://www.iroh.computer/services/hosting).
Собственный сервер — принятое рабочее направление, конкретный протокол и размещение
relay пока не зафиксированы.

## 3. Общие операции agent и постоянный процесс

В [B02](backlog.md#b02-простой-текущий-пайплайн-и-параллельная-работа-cligui)
пользователь выбрал общий процесс с локальным API команд и событий. Отложен
запуск Minecraft как отдельного сервера, а не агент передачи миров.

- [x] Есть `VanillaServer`, `HostService`, команды сервера и игрового туннеля.
- [x] Выбрана модель: агент владеет профилем и операциями, CLI и GUI одновременно работают с ним через команды и события.
- [ ] Выделить в `agent` общие операции библиотеки миров и передач; состояние серверной сессии и игрового туннеля расширять позже.
- [ ] Подключить CLI к `agent`, перенести туда общую координацию из интерфейсов без дублирования правил `core`.
- [ ] Спроектировать локальный API: доступ только владельцу, команды, события, ошибки и жизненный цикл операций.
- [ ] Реализовать постоянный процесс: завершение CLI или закрытие GUI не уничтожает его состояние; следующий клиент получает ту же сессию.
- [ ] Реализовать корректное завершение и запуск агента для обоих интерфейсов; автозапуск после перезагрузки и управление службой определить отдельно.

Подтверждённое направление: `cli/desktop → agent → core` с локальным API общего
процесса и подписками на изменения. Зависимость от библиотечных классов сама по
себе не обеспечивает совместную работу двух процессов.

## 5. Игра и передача роли хоста

Расширение игрового туннеля и единый сценарий миграции отложены. Исправление
данных игроков при передаче одиночного мира [B01](task_player_data.md) остаётся
ближайшей задачей и не требует готового игрового P2P-пайплайна.

- [x] Есть запуск из проверенной копии, сохранение, остановка и публикация новой версии.
- [x] Есть игровой туннель; локальные тесты проверяют байты и повторное подключение.
- [x] Есть тест последовательности смены хоста на тестовом процессе; это не готовая команда миграции.
- [ ] Поддержать несколько одновременных игровых клиентов: сейчас туннель обслуживает одного.
- [ ] Ввести состояние передачи роли: готовность получателя → сохранение и остановка → передача → проверка → запуск → переподключение участников.
- [ ] Определить право стать хостом и защиту от одновременного объявления двух активных хостов, включая обрыв связи и повтор команды.
- [ ] Реализовать обработку отказа нового сервера и явный возврат к прежнему хосту без потери принятой версии.
- [ ] Пройти полный сценарий на настоящем Minecraft с несколькими игроками и проверкой инвентарей.

Автоматическая миграция при внезапном отказе хоста, объединение миров и бесшовное
продолжение той же Minecraft-сессии в обязательный объём не входят: игроки переподключаются.

## Оценка готовности

До уточнения приоритетов B01–B17 ориентир по функциональному объёму первой
законченной версии составлял примерно 50–60%:
большая часть движка передачи и хранения есть, но ещё нужны свой координатор,
постоянный агент, согласованные интерфейсы, несколько игроков, единая ручная
миграция и приёмка. Это экспертная оценка по коду, не измерение оставшихся часов.

Под законченной версией здесь понимается перечисленный обязательный объём этапов
1–6. Расширенное удалённое администрирование, развитая система ролей, мониторинг,
собственный VPN и исследовательские оптимизации в эту оценку не включены.
Это исходная оценка прежнего объёма, а не автоматически актуальный процент для
расширенного списка B01–B17. Пересмотрите её после выбора ближайшего релизного
объёма, модели B02, режима relay, целевых ОС и завершения реальных испытаний.
