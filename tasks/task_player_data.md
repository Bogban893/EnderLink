# Данные игроков при передаче одиночного мира

[Пункт B01](backlog.md#b01-данные-игроков-при-смене-владельца-одиночного-мира) · Приоритет: высокий.

## Проблема и исходное предложение

Подтверждённый пользователем сценарий: A передаёт мир B, после чего B как новый
хост получает инвентарь A вместо собственного прежнего инвентаря. Состояние A
должно остаться закреплено за A, а B — получить свои вещи, которые были у него
в этом мире до принятия роли хоста. «Свои изначальные вещи» означает актуальное
состояние игрока перед сменой роли, а не сброс к инвентарю при создании мира.

Роль владельца мира меняется; принадлежность инвентарей игрокам не меняется.
Предложение команды: сохранять состояние владельца дополнительно по его аккаунту,
при приёме подставлять состояние нового владельца, а после игры обновлять его запись.

Направление разумное, но источник истины и преобразование зависят от формата мира.
Связывать состояние нужно с UUID Minecraft-игрока, а не именем друга или ID EnderLink.
Подтверждение этой связи и способ ввода UUID надо определить отдельно от авторизации
передачи: профиль EnderLink сам по себе UUID Minecraft не доказывает.

Ближайший объём — смена владельца одиночного мира; Dedicated Server отложен.
25 ноября 2026 года исследован дополнительный симптом на двух предоставленных
сохранениях Minecraft 26.3 / TLauncher: прежний хост входит к другу без вещей,
но после возврата мира получает их обратно. В файлах сохранились отдельные
UUID владельца и LAN-гостя с разными инвентарями; профиль владельца не был потерян.
Воспроизведена и исправлена безусловная замена профиля владельца пустым гостевым
при установке старого мира текущим кодом.

## Что уже есть и чего не хватает

- `PlayerDataInspector` определяет встроенный `Data.Player`, `singleplayer_uuid`
  и расположения файлов игроков.
- `WorldRepository.importLegacyPlayer` умеет одноразово перенести старого владельца
  из `level.dat` в `playerdata/<UUID>.dat`, не затирая существующий файл.
- Публикация защищена от исчезновения ранее сохранённых файлов игроков.
- Полный цикл «A играет одиночно → B получает и играет одиночно → A получает обратно»
  теперь реализован для закрытых копий: публикация с UUID обновляет запись активного
  владельца, а Desktop при установке готовит отдельную копию под UUID получателя.
  Синтетические NBT-тесты проверяют A → B → A. 25 ноября 2026 года цикл дополнительно
  проверен на копиях пользовательского мира двумя клиентами Vanilla 26.3 на одном
  компьютере с передачами через настоящие окна Desktop по TCP.
- LAN-пара получает запись последней синхронизации; при возврате выбирается
  изменившийся профиль, включая законно опустошённый инвентарь. Для разных
  неподтверждённых профилей Desktop запрашивает явный выбор. Отмена и ошибки
  метаданных оставляют установленный мир неизменным. Сценарий старого сохранения
  с сохранённым командным блоком и пустым гостем воспроизводится в
  `LanPlayerProfilesTest`. В локальном запуске Minecraft прежний хост сохранил
  командный блок при входе гостем, затем получил 2 золотых слитка; после обратной
  передачи у него сохранилось золото, у второго игрока при входе гостем — 4 железных
  слитка. Инвентари считаны из реальных клиентов и серверного потока; оба мира
  штатно сохранены. TLauncher, Windows и два физических компьютера ещё не проверены.

## Предлагаемая модель для исследования и реализации

1. Хранить в версии мира полное состояние всех известных игроков с устойчивыми UUID.
   Для каждого перехода определить актуальный источник; не поддерживать две
   конкурирующие записи без правила разрешения расхождений.
2. Для старого формата после закрытия мира сохранять актуальный `Data.Player`
   под UUID фактически игравшего владельца. Если файл UUID уже есть, отличать
   контролируемое обновление собственной записи от случайного затирания чужой
   или более новой версии; существующий безопасный импорт не ослаблять попутно.
3. Перед запуском полученного мира одиночно готовить отдельную локальную копию
   с состоянием выбранного нового владельца. Не менять владельца внутри общего
   опубликованного объекта и не выдавать ему вещи предыдущего хоста.
4. Для новых форматов использовать предусмотренную игрой связь с файлом игрока.
   В Java 26.1 `Player` заменён на `singleplayer_uuid`, а файлы игроков перемещены
   в `players/data`; универсальное дублирование в `Data.Player` здесь не подходит.
5. Если нового владельца ещё нет в сохранении, определить стандартный сценарий
   нового игрока без копирования чужого инвентаря и других персональных полей.
6. Сохранять полный NBT и связанные данные игрока; не ограничивать перенос списком
   предметов. Статистика и достижения также должны оставаться с правильным игроком.
7. Обновлять состояние после завершённой игровой сессии на копии с резервной версией.
   Постоянную запись в открытый мир и копирование «при каждом сохранении» отнести
   к исследованию [B09](backlog.md#b09-предварительная-передача-во-время-игры).

Это проектное предложение; конкретные правила чтения/записи следует подтвердить
на выбранных версиях игры до изменения NBT. Открытие старого мира новой версией
не равно обратимой конвертации; универсальную совместимость не обещать.

## Критерии приёмки

- [x] Описан фактический симптом: новый хост получает вещи предыдущего; пользователь подтвердил ожидаемую принадлежность инвентарей 24 ноября 2026 года.
- [x] Реализованы публикация с UUID, подготовка установленной копии и синтетический цикл A → B → A (`PlayerDataInspectorTest`, `MinecraftSavesTest`; `./gradlew :core:test :cli:test :desktop:test --offline`, JDK 21, 24 ноября 2026 года).
- [ ] Есть минимальная копия мира, воспроизводящая исходную проблему; записаны версия, UUID и переходы.
- [ ] До передачи зафиксированы разные инвентари A и B; после A → B новый хост B получает прежний инвентарь B, а состояние A сохранено под UUID A.
- [ ] После игры у B и возврата B → A игрок A получает собственное сохранённое состояние, а актуальные вещи B сохраняются за B; нет обмена, отката или смешивания инвентарей.
- [ ] Ближайшая приёмка: пройден цикл одиночный → другой одиночный владелец → обратно для поддерживаемых форматов.
- [ ] Позже, при возврате серверного объёма: проверить одиночный → выделенный сервер и сервер → одиночный.
- [ ] Проверены игрок без предыдущей записи, конфликт актуальности, ошибочный UUID и невозможность доказать принадлежность аккаунта.
- [ ] Проверены инвентарь, броня, эндер-сундук, опыт, здоровье, положение/измерение, достижения и статистика.
- [ ] Исходник и опубликованные объекты неизменны; прерванное преобразование не повреждает активную копию.
- [ ] Добавлены тесты NBT и реальная приёмка Minecraft; предупреждения GUI/CLI объясняют, какой игрок выбран и что будет изменено.
