# Данные игроков и сценарий передачи мира

## Данные игроков при смене хоста

Для смены владельца **одиночного** мира Desktop теперь просит UUID Minecraft-аккаунта
у каждой стороны. Отправитель выбирает закрытый мир и свой UUID. Для старого формата
EnderLink готовит отдельную копию и обновляет `playerdata/<UUID>.dat` из актуального
`Data.Player`; исходный каталог остаётся неизменным. Получатель указывает свой UUID:
при установке в `saves` приложение подставляет его сохранённый профиль в `Data.Player`,
а для нового игрока удаляет встроенный профиль прежнего владельца. Для формата с
`singleplayer_uuid` установка переключает ссылку на UUID получателя. Данные остальных
игроков и опубликованная версия не меняются.

После игры получатель должен закрыть мир и опубликовать **свою** папку из `saves` со
своим UUID перед обратной передачей. Без этого у друга останется старая версия.
При установке проверяются `session.lock`, прежний отпечаток установленной копии и
локальные изменения; изменённый мир не заменяется молча. UUID вводится пользователем:
EnderLink пока не подтверждает принадлежность Minecraft-аккаунта. Этот цикл проверен
синтетическими NBT-данными; поведение настоящей игры требует ручной приёмки.

### Связь профилей при разных UUID в LAN

В некоторых конфигурациях лаунчера UUID владельца одиночной игры отличается от
UUID гостя на LAN-сервере без проверки аккаунта. Последний вычисляется Minecraft
как `UUID.nameUUIDFromBytes("OfflinePlayer:<точный ник>".toByteArray(UTF_8))`.
Desktop позволяет явно связать эти два профиля через необязательное поле LAN-ника.
Ник используется только для вычисления этого дополнительного UUID, принадлежность
обоих профилей пользователь задаёт явно. Проверки аккаунтов управляемого сервера
и сетевого транспорта сохраняются.

При `publishSingleplayer(source, owner, guest)` актуальные данные хозяина копируются
в профиль `guest` внутри подготовленной версии. В современном формате
`singleplayer_uuid` должен совпадать с `owner`; при несовпадении публикация завершается
ошибкой с фактическим UUID. Для старого формата сначала сохраняется `Data.Player`.
При установке с такой связью существующий `guest` имеет приоритет над прежним
`owner`, поскольку он содержит результат последней игры этого участника в гостях.
Его NBT копируется в `owner`, корневой `UUID` заменяется, затем подготавливается
ссылка `singleplayer_uuid` или `Data.Player`. Копируются также достижения и статистика
в соответствующих старых или новых каталогах. Отсутствующие достижения и статистика
исходного профиля очищают устаревшие копии целевого профиля.

LAN-ник сохраняется в локальных настройках Desktop. UUID связи входит в локальную
метку установленного мира, чтобы смена настройки применялась даже к той же версии.
Старые метки читаются со значением связи по умолчанию `null`. Дисковый формат
репозитория и сетевой протокол передачи мира сохраняют прежние версии. Публикация
использует отдельную копию исходного мира, при установке сохраняются проверки локальных изменений,
`session.lock` и восстановление переключения после сбоя.

Связь применяется только при явно заполненном LAN-нике. Она переносит полный профиль
одного человека между двумя UUID. Перед включением для мира с уже возникшими пустыми
профилями нужно восстановить актуальные вещи из сохранённых файлов. Циклы смены
хоста и гостя проверяются синтетическими NBT-тестами для обоих форматов. Запуск через
настоящий лаунчер требует ручной проверки.

Для обычных Minecraft аккаунтов сервер должен запускаться с `online-mode=true` на каждом хосте. Имя игрока в EnderLink не должно определять владельца инвентаря: ключом остаётся UUID аккаунта, которым пользуется сам Minecraft. Агент теперь отклоняет явное `online-mode=false` в `server.properties`. Режим `online-mode=true` описан в [документации Paper](https://docs.papermc.io/paper/reference/server-properties/).

При передаче серверного мира `world-publish` и `world-send` включают **весь** каталог мира, в том числе файлы игроков, достижений и статистики. `agent host` копирует проверенную версию целиком, а после штатной остановки публикует её вместе с обновлёнными данными игроков. Отдельная таблица «ник → вещи» для такого перехода не нужна и могла бы потерять данные при смене имени. Нельзя переносить только `region` или только `level.dat`.

Формат каталога зависит от версии игры. В Minecraft Java 26.1 Mojang перенесла `playerdata` в `players/data`, а `advancements` и `stats` — в `players/advancements` и `players/stats`. В той же версии тег `Player` в `level.dat` заменён ссылкой `singleplayer_uuid` на файл игрока. Это описано в [заметках Mojang о 26.1](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-1). Поэтому EnderLink передаёт дерево без попытки угадать расположение файлов по имени.

**Отдельный случай — первая публикация старого одиночного мира.** До 26.1 данные владельца могли находиться в `level.dat` в теге `Player`; серверная игра с тем же аккаунтом должна получить данные в файле, названном UUID. Команда `world-import-owner --repository <каталог> --owner-uuid <UUID>` выполняет одноразовый перенос после `world-publish`:

1. Пользователь выбирает закрытый одиночный мир. EnderLink проверяет структуру `level.dat` и наличие `playerdata` и `players/data`, без ручного выбора версии. Это уже делает `PlayerDataInspector`; `world-publish`, `world-status`, быстрая отправка и `agent host` теперь предупреждают о возможной потере данных владельца. Если `level.dat` нельзя разобрать, интерфейс сообщает, что проверка не удалась.
2. Пользователь явно вводит полный UUID владельца своего Minecraft аккаунта. Ник не служит доказательством личности; вход в аккаунт внутри EnderLink пока не реализован.
3. EnderLink переносит **весь** NBT `Data.Player` как серверный `playerdata/<UUID>.dat`, включая инвентарь, эндер-сундук, опыт, положение и другие поля. Существующий файл того же UUID не перезаписывается.
4. Рабочая копия публикуется как новая версия. Исходный одиночный мир и предыдущая версия репозитория остаются доступны для отката. Затем версию отправляют через `world-send` без `--source` исходного мира. Проверка заканчивается входом тем же аккаунтом на тестовый сервер совместимой версии.

Импорт проверен на синтетических NBT данных; открытие результата в настоящем Minecraft ещё требует проверки. Для миров, которые уже использовались на выделенном сервере, перенос данных игроков выполняется вместе с миром. Разные версии миров поддерживаются на этапе определения расположения файлов; это не означает, что сервер одной версии может безопасно открыть мир другой версии. Запуск и первый вход нужно проверять на совместимой версии Minecraft.

## Сценарий пользователя

1. **Отправитель:** закрывает мир или останавливает сервер. Интерфейс показывает, какой мир и какая версия будут отправлены. `world-send --source <мир> --repository <хранилище> --peer <друг>` теперь совмещает публикацию и отправку.
2. **Получатель:** выбирает отдельное хранилище и запускает `world-receive`. До приёма видит имя друга и выбранный путь, после — ID версии и путь готового мира. При обрыве повторяет команду с тем же хранилищем; проверенные блоки используются повторно.
3. **Передача:** прогресс разделяется на подготовку/сканирование, поиск недостающих блоков, сеть и проверку/активацию. Нужно показывать объём новых данных и повторно использованных данных, а не только общий процент.
4. **Запуск:** новый хост запускает `agent host` с подготовленной версией. Интерфейс явно указывает, что сервер берёт копию мира, и не предлагает редактировать этот каталог одновременно с сервером.
5. **Конфликт:** при двух независимо изменённых версиях интерфейс показывает обе версии и предлагает выбрать, какую запустить; не делает автоматическое слияние и не подменяет активный мир без выбора.

Текущий CLI поддерживает публикацию, передачу, повтор после обрыва и выбор версии. Он выводит этапы передачи, путь хранилища получателя и действие при конфликте. Следующий UX шаг — единый экран для обеих сторон с состоянием ожидания друга и явным подтверждением смены хоста.

Для фонового запуска есть `agent host-service`: он работает под менеджером служб без чтения консоли, при штатной остановке сохраняет и публикует мир. Встроенного самозапуска, управления несколькими сессиями и автоподнятия сервера после аварии нет; повторный запуск с занятым каталогом сессии сознательно блокируется до проверки оставшегося мира.
